# Feature Audit Summary

## Top 10 features I actually built

1. Telegram and CLI goal creation with approval-gated planning: `/new_goal` and `goal new` create persisted runs, generate plans, and stop for approval or plan-only review before execution (`src/telegram/goal-commands.ts:483`; `src/commands/goal.ts:90`; `src/commands/goal.ts:236`; `src/commands/goal.ts:286`).
2. Structured planner contract and validation: planner output is constrained into typed steps, dependencies, backend assignments, success criteria, constraints, and build-gate metadata (`src/goal/planner.ts:14`; `src/goal/types.ts:57`; `src/goal/goal-schemas.ts:50`).
3. Independent plan autocheck and revision loop: a read-only reviewer can inspect generated plans and write revision artifacts before approval (`src/goal/plan-autocheck.ts:28`; `src/goal/plan-autocheck.ts:445`; `src/goal/plan-autocheck.ts:819`).
4. DAG modeling and critical-path-aware scheduling: planned work becomes a dependency graph, and runnable tasks are ordered with critical-path data (`src/goal/dag-render.ts:1`; `src/goal/dag-render.ts:62`; `src/goal/cpm.ts:57`; `src/goal/agent-executor-helpers.ts:170`).
5. Multi-backend worker orchestration: PI, Codex, and Claude Code style workers are normalized behind a shared task-runner/result contract with availability checks (`src/goal/backend-types.ts:8`; `src/goal/backend-availability.ts:114`; `src/goal/task-runner.ts:5`; `src/goal/cli-runner.ts:40`; `src/goal/pi-runner.ts:101`).
6. Worker prompt and JSON result-file protocol: CLI worker prompts include constraints, hard-denies, completed-task context, lessons, and a required result-file protocol (`src/goal/cli-worker.ts:576`; `src/goal/cli-worker.ts:628`; `src/goal/cli-worker.ts:782`; `src/goal/cli-worker.ts:809`).
7. Durable run state, worker artifacts, and attempt bundles: runs, prompts, stdout/stderr, result JSON, repair logs, attempt bundles, and working journals are persisted for audit and handoff (`src/goal/run-store.ts:65`; `src/goal/cli-worker.ts:294`; `src/goal/cli-worker.ts:819`; `src/goal/attempt-bundle.ts:17`; `src/goal/run-journal.ts:7`).
8. Resume, crash reconciliation, and feedback revision: stale in-progress work can be reconciled, explicit resume continues persisted runs, and operator feedback revises remaining work while preserving completed work (`src/goal/run-store.ts:131`; `src/commands/goal-resume.ts:456`; `src/commands/goal-resume.ts:587`; `src/goal/feedback.ts:46`; `src/goal/feedback.ts:90`).
9. Review and build gates: completed runs can go through read-only diff review and sequential verification commands with captured output and failure classification (`src/goal/post-execution-review.ts:168`; `src/goal/post-execution-review.ts:206`; `src/goal/build-gate.ts:58`; `src/goal/build-gate.ts:115`).
10. Goal-specific learned rules and safety guardrails: completed runs can produce scoped lessons for later worker prompts, while hard-deny policies, capability enforcement, sandbox prompt contracts, and credential-like env stripping reduce risky worker actions (`src/goal/lessons.ts:25`; `src/goal/lessons.ts:174`; `src/goal/agent-executor.ts:1024`; `src/goal/hard-deny.ts:52`; `src/goal/capability-enforcement.ts:80`; `src/goal/claude-code-env.ts:7`; `src/goal/cli-worker.ts:628`).

## Top 5 things that make SmithersBot impressive

1. It treats coding-agent work as an executable dependency graph rather than a single prompt or flat checklist, with typed plan structures, DAG rendering, and critical-path scheduling (`src/goal/types.ts:57`; `src/goal/dag-render.ts:62`; `src/goal/cpm.ts:57`).
2. It separates planning, autocheck, approval, execution, review, and build verification into distinct persisted stages, which makes the agent loop more inspectable than a one-shot chat workflow (`src/goal/cli-planner.ts:819`; `src/goal/plan-autocheck.ts:819`; `src/commands/goal.ts:286`; `src/goal/post-execution-review.ts:206`; `src/goal/build-gate.ts:115`).
3. It normalizes several local worker backends behind one result protocol, so the orchestrator can handle completion, blockage, failure, and strategy-change outcomes consistently (`src/goal/task-runner.ts:21`; `src/goal/cli-runner.ts:86`; `src/goal/cli-worker.ts:809`).
4. It leaves an unusually rich audit trail for agent work: prompts, stdout/stderr, result files, attempt summaries, working journals, run state, and build-gate metadata are first-class artifacts (`src/goal/cli-worker.ts:294`; `src/goal/cli-worker.ts:327`; `src/goal/attempt-bundle.ts:137`; `src/goal/run-journal.ts:25`; `src/goal/run-store.ts:431`).
5. It combines phone-based operator control with continuity mechanisms: Telegram approvals/replies, durable run metadata, stale-run reconciliation, explicit resume, feedback revision, and learned-rule injection all support longer coding tasks (`src/telegram/goal-commands.ts:483`; `src/telegram/goal-router.ts:205`; `src/goal/run-store.ts:131`; `src/commands/goal-resume.ts:587`; `src/goal/feedback.ts:90`; `src/goal/lessons.ts:174`).
